# nuzlocke.gg version 1: technical design

How version 1 is built: the platform, the game data, the changes to a Run, storage, and the headcanon integration. What the app does is in [product.md](product.md), including [the domain model](product.md#the-domain-model), which this document uses throughout. Screens are in [screens.md](screens.md) and tests in [testing.md](testing.md).

## Platform and prerequisites

- **Hosting and stack**: Next.js App Router in `apps/web`, React 19, the shadcn component package in `packages/ui`, Tailwind v4, Neon Postgres, Vercel (Pro; no Skew Protection, ADR 0003), Auth.js with Google sign-in and database sessions, Drizzle through the Neon WebSocket `Pool` driver (not the HTTP driver).
- **Changes to a Run go through headcanon** (a published version that includes the fixes of NUZ-25 to NUZ-31, with `serializable-result@0.1.0`), installed from npm, never copied in. The headcanon checkout still says `0.1.0` and has no tag, so publish a new version before the build. Live signals go through headcanon's Ably invalidations.
- **Before the build**: upgrade to TypeScript 6 and Node 22 or later in local development, CI, and Vercel; update `@types/node`. Read `AGENTS.md` and the Next.js docs under `node_modules/next/dist/docs/` before any app code: this Next.js version has breaking changes.
- **One change to headcanon is required before the Run screens** ([Headcanon gaps](#headcanon-gaps)). Otherwise the Run root uses headcanon's standard Next binding with router refresh, `withVisibilityRefresh`, and a persisted queue ([Headcanon integration](#headcanon-integration)).

## Game data

- **The seam** (ADR 0001): the project owns one game data format. Importers (PokeAPI CSV at a pinned commit; later the pret decompilations) and hand-written files compile it before a release. The compiled files ship with the app in a workspace package and are read through one reader with one asynchronous "load this Map" function and pure functions over the result. The app never calls a data source; Neon holds no game data.
- **The unit is a Map with its Games inside.** A Map gives: its Games (identifier and name); its Places in one hand-written play order, each with a name for every Game of the Map (every Game has every Place; Black City and White Forest are one Place with two names), the Starter Place first, Event Places last; encounter tables per Place and Game as Species and Forms in **method groups** (Emerald: Walk, Surf, Fishing, Rock Smash, Static, Roaming with origin Wild; Gift; Trade; the list grows when a Game needs a group, and each group has a default origin); all Species of the Game's generation (386 for Emerald and FireRed/LeafGreen, 493 for Platinum), each with its National Dex number (the sort key for "National Dex" order in the Box), one or more Forms, and each Form with its types in that Map (the Games of a Map share one generation, so types are per Map); evolution links filtered to the Map and an Evolution Line identifier per Species (hand-written overrides allowed; Shedinja has its own line, because it is recorded as its own Encounter). The line identifier is the earliest Species of the chain (`pichu` for the Pikachu line); it is derived, never stored, and compared inside one Map only. No levels, rates, conditions, floors, images, level caps, or translations. Names are English.
- **An importer supplies only repeatable wild tables and Species facts.** One-time encounters (gift, trade, static, roaming) are always hand-written and checked against the game's source. **Importers are one-off generators whose output is committed**: a build never calls PokeAPI for game data, and a re-import is reviewed as a `git diff`. The one exception is the sprites, which the build copies from a pinned commit (below). Generated files and hand-written files live apart, and a generator writes only its own files, so a re-import never erases a hand edit. The compile is merge, validate, and the **permanence check** (it stops when a released identifier would no longer resolve or would change meaning).
- **A Place is the recorded location.** The Starter Place is the one exception (each Map has one). An egg's Place is where it hatched. An in-game trade's Place is where the player received it. Two spots with one recorded name are one Place (Underwater). Counterpart places (Black City and White Forest) are one Place with a name per Game. A roaming Species is in the Roaming group of each route where it can appear. Nothing from outside the cartridge (bonus discs, Dual-slot); a Custom Place covers that.
- **Encounter tables are suggestions only.** They order the Species list in the record Drawer and decide nothing else. There is no "Species not found here" Warning. A randomized game is a Run on its base Map.
- **Forms**: a Form that differs in type is required; a Form that differs only in look is optional. Modes (Mega, Aegislash) are not data. A Regional Variant is a Species of its own; its Evolution Line follows the links (Alolan Raichu is in the Pikachu line; Alolan Raticate is not in the Raticate line). Manaphy and Phione are two lines.
- **Identifiers are our own, readable, and permanent once released** (`emerald`, `vulpix`, `vulpix-alola`; a Place id unique in its Map; a ROM hack prefixes its new Species). A Journey stores its Game id; an Encounter stores Place, Species, and Form ids; a Pokémon stores Species and Form ids. No foreign keys to game data and no data revision on a Run. Corrections reach existing Runs. An unknown identifier renders as unknown; the reader never substitutes.
- **Version 1 ships three Maps, built in this order**: Emerald (one Game, about 77 Places, 41 one-time encounters); FireRed and LeafGreen (the first paired Map, two Games on one Map, about 82 Places, 43 one-time; roaming beasts all in Roaming); Platinum (the first Generation 4 Map, about 90 Places, 44 one-time; Wormadam, Shaymin Sky, and Arceus Forms differ in type; Arceus plate Forms are hand-written because PokeAPI types them Normal; Rotom's Forms are all Electric/Ghost in Platinum). No Mass Outbreak data is needed. Generation 1 is not in version 1. More Maps come after launch as data files only.
- **The format** (decided in "Game data format", NUZ-44; the prototype is on the branch `prototype/nuz-44-game-data-format`): one compiled JSON file per Map (`dist/<map>.json`), built by a Turbo task and not committed. A Place has a `kind` (`starter`, `standard`, `event`), a name per Game, and a table per Game of method groups; entries keep the source order (an importer writes the most common first) and no rates. A Form identifier is unique in its Species (a Run stores the pair); a Species with one Form uses `base`. The project-wide method list (`sources/methods.yaml`) gives each group a name, a default origin, and whether it is one-time.
- **Sources** (`sources/maps/<map>/`): hand-written files are YAML (`map.yaml` with the Games and the Places in play order, each Place naming the source areas it groups; `one-time.yaml`; `corrections.yaml`); importer output is JSON in `generated/<importer>.wild.json` and `generated/<importer>.species.json`, one intermediate shape for every importer, so the pret importer plugs in without a compile change. Species facts are copied into each Map. **Merge rule**: hand-written data wins only through a correction that states what it expects in the generated data (a row present or absent, the old types, a link present or absent); when a re-import changes that, the compile stops and names the correction. One-time groups (Static, Roaming, Gift, Trade) are hand-written only, and an importer row in one of them stops the compile. Every source area belongs to exactly one Place or is ignored with a reason.
- **Permanence check**: a committed lock per Map (`released/<map>.lock.json`) lists every released Game, Place, Species (with its dex number), and Form. It is created at launch; before launch identifiers change freely. The compile adds new identifiers to the lock, and CI runs it frozen, so it fails when the lock would change or when a locked identifier fails. The check proves that every locked identifier resolves, a Game stays in its Map, and a Species keeps its dex number. Names, order, kind, types, and tables are corrections. Reuse of an identifier for a different thing is caught only in review. Identifiers are lowercase words joined by `-`; a ROM hack prefixes its new Species with `<hack>:`.
- **The reader**: `listMaps()` (sync catalog: New run Map Drawer) · `loadMap(mapId)` (async, cached; every Run screen) · `getGame` (Run list row, chips; with a `monogram`) · `placesOf(map, game)` (Encounters tab) · `placeName(map, place, game)` · `suggestions(map, place, game)` (record Drawer groups and default origin) · `getSpecies`, `getForm`, `hasFormChoice` (rows, the Form control) · `searchSpecies(map, query)` (record Drawer, Evolve "Other species", Correct; ignores case, accents, and punctuation; digits match the dex number) · `nextInLine(map, species, form)` (Evolve; keeps the Form id when the target has it, else its first Form) · `evolutionLineOf` (Duplicate Clauses, the "Same line as" mark) · `primaryType`, `formTypes`, `typesOf` (Type Restriction, Box filter) · `dexNumber` (Box sort) · `progressTotal(map)` (Run list, Attempts, preview card: every Place of the Map except Event Places) · `spriteUrl(map, species, form)` and `unknownSpriteUrl` (the Sprite component; the only way the app gets a sprite). An unknown identifier returns `undefined`; the screen says unknown and a Rule skips that Pokémon.
- **A future per-Map Milestone section** must fit the format without a new Map: an unordered set with Map-defined kinds, opponent data per Game, added later as an optional top-level `milestones` key of the compiled Map. Nothing is built for it in version 1.
- **Sprites**: one set for every Map, the PokeAPI default front sprites (Black/White style, 96 × 96). A build step copies them from a pinned commit of the PokeAPI sprites repository next to the compiled data; they are served from Vercel with a long cache and are not committed to git. A Form with no sprite shows the first Form of its Species; never letters. The repository README states that the sprites are not under the project's licence. A hand-written `sources/sprites.yaml` names the PokeAPI file for a Form that needs one: a Regional Variant (it shares its dex number), a ROM-hack Species, or a Form that PokeAPI names by Pokémon id (`deoxys/attack: "10001"`); else a Form other than the first uses PokeAPI's `<dex>-<form>.png` when it exists. The build writes `dist/sprites/<species>/<form>.png`, and the web build copies them to `/sprites/`. The paths stay the same across deploys, so a tab still on an old build never asks for a sprite that is gone; they are cached for a week (`public, max-age=604800`), not `immutable`, because a new pin or override changes a sprite's bytes. **Rendering** (NUZ-47): no circle and no clip. The sprite sits in a box at the prototype sizes, 20 (chip), 28 (small row), 32 (pill), 36 (list row), 48 (peek), 64 (Pokémon header), and is drawn at 4/3 of the box, centred, so it fills the box and its empty margin spills a little past it (a container needs a few px of padding around it). It is pixelated from a drawn size of 48 px (1× or more on a 2× screen) and smooth below. Its label is the Species name. An unknown Species or Form shows the unknown sprite, PokeAPI's `0.png` (a grey "?" on a white disc), labelled "Unknown Pokémon"; a sprite that fails to load (offline, not yet cached) shows the unknown sprite and keeps its label. A dead Pokémon's sprite is dimmed by the screen.

## The named changes to a Run

On a Journey (the actor's own only): 1 Record an Encounter; 2 Correct an Encounter; 3 Remove an Encounter (its Pokémon goes too); 4 Rename a Pokémon; 5 Evolve a Pokémon; 6 Move a Pokémon (a list of moves committed together: the Party editor draft and the full-Party swap are one change); 7 Record a death (one living Pokémon; optional level and cause); 8 Edit a death (level and cause of a dead Pokémon); 9 Undo a death (one dead Pokémon); 10 Remove a Pokémon; 11 Change the Form of a Pokémon.

Details the build needs on three of them:

- **2 Correct an Encounter** edits the Species and Form met and the origin, and nothing else. A change of the **Species met** also sets the current Species and Form of the Encounter's Pokémon when it still has the old met Species and no evolution line; a Pokémon that evolved stays as it is. On a Failed Encounter it can set or clear the Species, and set the Form and origin. The location, the Slot, the outcome, and the time of entry are not editable: the player removes the Encounter and records it again (in a Soul Link, "Record yours" puts it back into the right Slot).
- **5 Evolve a Pokémon** with "Next in its line" adds an evolution line to the history. Its "Other species" option is a **correction**: when the Pokémon has evolution lines it edits the target of the latest one, and when the chosen Species is the one that latest line started from (an accidental Treecko to Grovyle, corrected back to Treecko) it removes that line instead; when the Pokémon has no line it sets the Species and Form with no line. A wrong Species is thus fixed without a false history.
- **7, 8, 9 Deaths** have no death identity. **Record a death** changes a living Pokémon to dead and is refused as `gone` on a Pokémon that is already dead. **Edit a death** changes the level and cause only and is refused as `gone` on a living Pokémon. **Undo a death** changes a dead Pokémon back to alive and is refused as `gone` on a living one. In a race between two of the same player's devices, a stale Undo can undo a newer death; it is visible and one tap to fix, accepted. The Graveyard box on the Pokémon screen opens Edit a death. The time of a death is not editable in version 1.

On the Run (any player): 12 Add a Custom Place; 13 Rename a Custom Place; 14 Remove a Custom Place (refused while it has Encounters); 15 Set the Rules (a partial map of the keys that changed).

These 15 are the protocol `run.v1`. Only an **Active** Run admits them. While a Soul Link waits, the Rules screen is read only: the creator sets the Rules on the New run screen, and every player can change them from the first moment of Active. Nothing is recorded before the start, so no Warning differs.

Run-level actions outside the protocol, each a writer under the Run lock (ADR 0002): create a Run (private by default); join, leave, Start the Run (Waiting only); Rename and Visibility (any state); House rules (any state, last write wins); Mark as failed (optional cause), Mark as complete (Active); Reopen (Finished, newest Attempt only); Try again (Failed, newest Attempt, no deleted Player, refused when a next Run exists); Archive and Unarchive (any state, the newest Attempt of the Chain only). Whether any of them joins `run.v1` is a build decision.

Account-level actions outside the Run: set the Display Name (no Run lock, no Ably signal); delete account (writes the tombstone, then takes the Run lock of every Run it touches; [Player identity](#player-identity)).

## Rules and Warnings

The Rules, what each one checks, and the Whiteout bar are in [product.md](product.md#rules-and-warnings). The build needs:

- **Storage**: a Run stores all nine values from creation; an absent key is Off (ADR 0007).
- **Dependency**: the shared `setRules` function normalizes the Duplicate Clause dependency; no database constraint.
- **Warnings are computed in the browser only**, by one pure function over the displayed Run (canon plus pending predictions) and the game data. The server never computes a Warning for a write. A Warning is never a Refusal. Nothing about Warnings is stored.

## Soul Link: access, Slots, and order

What the players see and do is in [product.md](product.md#soul-link). The build needs:

- **The `canChange` policy** is one function, run on the server inside each change under the Run lock. It has two halves that headcanon treats differently: **access** (a player changes their own Journey only, changes 1 to 11; no owner or creator role) is decided in `admit`, which can only allow or deny, so a change to a partner's Journey is a denial with no public reason; **state** (only an Active Run admits a `run.v1` change, [The named changes to a Run](#the-named-changes-to-a-run)) is decided in `execute` from the locked state, so it is a public Refusal ("wrong state") that the toast can explain. Run-level changes (12 to 15, name, visibility, House rules, the lifecycle actions) are open to every player.
- **A new Slot is a plain ordinal**: the client sends max + 1 of the Slots it sees. Two partners who make a new Slot at one Place at the same time thus land in one Slot, because the unique index is per Journey. Only the same player on two devices can collide, and that gets the ordinary `slot-taken` Refusal. The UI refers to Encounters by id, never by ordinal.
- **Changes at the same time**: the server applies changes to one Run one at a time. Set the Rules sends only the changed keys, so two players' toggles both hold.

## Player identity

What a Player is, the Display Name, and what Delete account keeps are in [product.md](product.md#player-identity). The build needs:

- The Display Name lives on the account; history lines and Journeys store the player id, never the name text. A rename sends no Ably signal.
- The invite link is remembered across sign-in in a cookie.
- Theme is a browser preference through next-themes, not a column.
- **Delete account** (ADR 0006) reduces the account row to a tombstone (Google id, email, Display Name, name, and image nulled; sessions and OAuth accounts deleted) that renders as "Deleted player". `requireActor` refuses a tombstoned user.
- **No Player lock.** Delete account is one transaction: the tombstone in **one UPDATE** that sets `deleted_at` and nulls the email, Display Name, name, and image together (the schema's CHECK forbids setting one without the others), then each of the Player's Runs under its Run lock, in ascending Run id order. Create, join, and Try again check `deleted_at` through `requireActor` at their start. A create or join on one device in the same instant as a deletion on another can leave a stray row (a private solo Run nobody reaches, or a "Deleted player" in a waiting Run); accepted.

## Storage

The schema below is the decision of "Storage design", trimmed to the decision-rich parts. The Drizzle schema lives in the web app; drizzle-kit migrations are committed as SQL and run at deploy. Enums are Postgres enums, and a value is only ever added. Game data is referenced by its released text identifier with no foreign key.

```
users                       (= Player; the Auth.js adapter table, defined by us)
  id uuid pk · email null (unique where not null) · email_verified · name · image
  display_name null, check 1–30 chars · deleted_at null
  check: deleted_at set ⇒ email, display_name, name, image all null
accounts, sessions          adapter columns; user_id fk users cascade; database sessions
headcanon_mutation_receipts exactly as shipped by headcanon

runs
  id uuid pk (random v4, server) · kind enum(solo, soul_link) · state enum(waiting, active, failed, complete)
  name · map_id text · visibility enum(private, link) · rules jsonb {ruleId: bool} · house_rules null, check ≤ 2000
  archived bool · created_at · started_at null · finished_at null · fail_cause null · last_changed_at · revision bigint
  previous_run_id null UNIQUE fk runs (no action) · chain_id fk runs · attempt_number int
  invite_token null UNIQUE
  checks: waiting ⇒ soul_link · fail_cause ⇒ failed · finished_at ⇔ failed or complete
          invite_token ⇒ waiting · attempt_number = 1 ⇔ previous_run_id null
  UNIQUE(chain_id, attempt_number)

journeys
  id uuid pk (server) · run_id fk runs cascade · player_id fk users (no action) · game_id text · joined_at
  UNIQUE(run_id, player_id) · UNIQUE(run_id, id) · index (player_id, run_id)

custom_places
  id uuid pk (client) · run_id fk runs cascade · name · UNIQUE(run_id, id)

encounters
  id uuid pk (client) · run_id · journey_id, fk (run_id, journey_id) → journeys cascade
  place_id text null · custom_place_id null, fk (run_id, custom_place_id) → custom_places (no action)
  slot_ordinal int ≥ 1 · origin enum(wild, gift, trade) · outcome enum(caught, failed)
  species_id null · form_id null · entered_at
  checks: exactly one of place_id / custom_place_id · caught ⇒ species_id · species_id ⇔ form_id
  UNIQUE(journey_id, id) · partial UNIQUE(journey_id, place_id, slot_ordinal) · partial UNIQUE(journey_id, custom_place_id, slot_ordinal)
  index (run_id, place_id)

pokemon
  id uuid pk (client) · journey_id · encounter_id, fk (journey_id, encounter_id) → encounters cascade
  species_id · form_id · nickname null · in_party bool
  died_at null · death_level null · death_cause null · removed_at null
  checks: death_level or death_cause ⇒ died_at
  UNIQUE(encounter_id)

evolutions
  id uuid pk (client; the history line id) · pokemon_id fk pokemon cascade
  species_from · form_from · species_to · form_to · entered_at
  index (pokemon_id)

```

- **The database enforces**: one next Run per Failed Run; one Attempt number per Chain; a tombstone with no identifying columns; one Journey per Player per Run; one Encounter per Journey per Slot (the `slot-taken` Refusal is this unique violation); a Custom Place cannot go while an Encounter names it; every child row sits in its own Run and Journey (composite foreign keys); a Caught Encounter has a Species; Species and Form come together; an invite only on a waiting Run; one Pokémon per Encounter; level and cause only on a death.
- **The commands enforce, under the Run lock**: the Party of six; two or three players; a Journey's Game within the Run's Map; the state transitions; the Try again refusal; removed rows excluded from every read of the Party, Box, and Graveyard; `last_changed_at` set with every revision bump. The unique index on the Pokémon's Encounter and the index on the evolution's Pokémon serve the Run load and the cascade on Remove an Encounter; a foreign key creates no index on its own.
- **Deaths** are three columns on the Pokémon (`died_at`, `death_level`, `death_cause`) with no identity; the commands of [The named changes to a Run](#the-named-changes-to-a-run) test the life state under the Run lock. `in_party` is left as it was at death so Undo restores the same spot; if the Party filled meanwhile, Undo sends it to the Box.
- **Removing** an Encounter deletes it and its Pokémon. Removing a Pokémon sets `removed_at` and keeps the row, so its evolution lines and its Encounter stay.
- **Chains** delete as `DELETE FROM runs WHERE chain_id = $1`; deleting the root alone does not cascade through the Chain.
- **History** reads Encounter rows, evolution rows, and the death columns, ordered by `entered_at` then id; the player of each line is the Journey's Player.
- **Run state dates**: the date columns of a state change are overwritten on Reopen; there is no state log.
- **Progress** has no stored counter: a count of distinct Place ids per Run with the denominator from the game data (Custom and Event Places excluded on both sides). The remaining count beside "Add a location" is the denominator minus that count.
- **The order of the Encounters list** has no stored order either: each Place sorts by the earliest `entered_at` of its Encounters in the Run, over every Journey, so a Soul Link shares one list. A Custom Place with no Encounter sorts by the time in its UUID v7 id. The Starter Place always comes first. A Progress cell is Missing for the viewer when the Place counts through another Journey only. The play order of the game data no longer orders the tracking screen; the Add a location Drawer sorts by name.
- **Box sort** Newest and Oldest use the Encounter's `entered_at`, then the Pokémon id (UUID v7).
- Timestamps kept on purpose: `runs.created_at`, `runs.last_changed_at`, `journeys.joined_at`. None on users, encounters, pokemon, or evolutions.

## Headcanon integration

- **One axis per Run**: one axis family, `runAxis = defineAxis("run", z.uuid())` from `headcanon`, so `runAxis.of(runId)` is the axis `run/<runId>`. The loader, the commands (`stamp.record`), and the token endpoint all use it. The revision is on the Run row as a bigint read as a number. Later screens (the Run list) get their own collection axis.
- **Every writer takes the Run lock** (ADR 0002): in one transaction, `SELECT … FOR UPDATE` on the Run row before any read or write in the Run; write; `revision = revision + 1`; after commit, announce the stamp (headcanon commands through the generated action; other writers through headcanon's external-commit helpers with the Ably publisher). `throwMutationContention()` stays only as a guard.
- **Deadlines** (kept on purpose; `idle_in_transaction_session_timeout` stops a leaked transaction from holding the Run lock for every player): pool connection timeout 2 s; per-connection `lock_timeout` 2 s, `statement_timeout` 3 s, `idle_in_transaction_session_timeout` 5 s; `maxAttempts` 2; the route segment `maxDuration` 9 s on each page that calls the Run action. Starting values to tune.
- **One protocol `run.v1`**, one predicted root per Run mounted in the Run's route layout, keyed by the player id and the `runId`, so an identity change mounts a new root with its own queue; the Pokémon screen and the Party editor are routes under that layout and share one queue. The state type is the full Run as the screen needs it: Rules, Journeys (player, game, Encounters with Slot, Pokémon with location and death), Custom Places, history lines, and the Slot ordinals in use at each Place. Each mutation declares its Refusal kinds as a synchronous `refusal` schema.
- **Stable inputs**: everything random or clock-based is in the args, chosen once when the invocation is built. New ids (Encounter, Pokémon, Custom Place, history line) are client UUID v7. `enteredAt` is the client clock when the player saved, stored as `min(enteredAt, now)`; a retry hours later keeps the original time. The new-Slot ordinal is the client's prediction, a plain number ([Soul Link: access, Slots, and order](#soul-link-access-slots-and-order)).
- **One shared check per change**: a browser-safe domain module exports, per change, a strict `check(state, args) → Result<Effect, Refusal>` and `apply(state, effect) → state`. The predictor runs `check` then `apply`, nothing else. A replay over canon that already holds the player's own change (it reached canon through a partner's invalidation before its own acceptance) may be refused; headcanon then drops only the predicted effect and keeps waiting for the server's outcome (headcanon withdraws a change as `replay-refused` only when no delivery of it may have committed), so the screen is right and `onConflict` only logs. A change that sets a value (rename, Form, Set the Rules, Edit a death) is a no-op Effect when the value is already set, not a Refusal; the server accepts it with `acceptMutation({ unchanged: true })` and does not bump the revision, because headcanon refuses an accepted change with an empty stamp. The server runs the same strict `check` under the lock, then the **server-only game-data gate** (a Game Place, Species, or Form must exist in the Journey's Game, else `unknown-entry`; a Custom Place is checked against the locked state), then writes rows explicitly from the effect. No diffing.
- **Refusal kinds** (a discriminated union; kinds are only added): `party-full`, `slot-taken`, `custom-place-in-use`, `unknown-entry` (server only), `gone` (something gone or in the wrong state; a new kind for "wrong state" is permitted). A full Party on a new catch sends it to the Box; it is not a Refusal.
- **Actor and scope**: `requireActor` reads the Auth.js session and returns the user id; redirect to sign-in without one. It is the `actor` of the binder (`createMutationBinder` from `headcanon/server`). Receipt scope is the user id. `screen` checks that the actor has a Journey in the Run named in the args, outside the transaction (this also guards replay of stored receipts). `admit` rechecks membership and the access half of `canChange` under the lock and passes the locked Run state to `execute` as evidence; `execute` applies the state half of `canChange` and the shared `check`, both as public Refusals.
- **Canon loader**: one uncached loader that reads the Run row with its revision and every child table in one `REPEATABLE READ READ ONLY` transaction and returns the canon with the axis revision. The Run layout renders it under Suspense; the provider is keyed by the player id and the `runId` (the Reader's observed root by the `runId`). The same reader feeds `admit`.
- **Live signals**: a Soul Link root uses Ably invalidations, with no polling fallback; a solo root has no realtime transport. headcanon's Ably adapter already reports a gap, and so refreshes, after a dropped connection or a channel reattach without resume. Every Run root also refreshes when the page becomes visible again, which covers a lost publication (a failed server publish is not retried) and a rename: the root's invalidation adapter is wrapped in headcanon's `withVisibilityRefresh`, around the Ably adapter on a Soul Link and around `createNoRealtimeInvalidationAdapter()` on a solo Run. While the browser reports itself offline, the wrapper holds the refresh and sends it on the `online` event. The Ably publisher's required `onFailure` reporter logs a failed publication. A Run root never refreshes on a timer: a query to Postgres more often than every 5 minutes keeps Neon compute awake while a tab is open. The token endpoint parses each requested axis with `runAxis.parse` and rejects the whole request if any axis does not parse or is not a Run where the actor has a Journey **or** a Run readable by link. It passes `runAxis.of(id)` for the Runs it read (never the browser's strings) to `createAblyAxisTokenRequest`: subscribe-only, the user id as client id, and a 10-minute TTL. A Reader without an account gets no client id, as headcanon's realtime guide documents ("Serve viewers without an account"). A sign-in or sign-out replaces the connection. A Reader gets a **`createNextObservedRoot`** (no queue, no `mutate`), with the same adapter as the Run's players. The Reader's loader reads no session (it checks only that the Run is readable by link) and never calls `requireActor`. When the Run turns private, the next token renewal is refused and the next refresh shows the private page. One Ably namespace per environment, each preview tied to its database branch: a Neon branch copies its parent's rows, so two branches can hold the same Run id, and headcanon names a channel by namespace and axis only.
- **The Run root refreshes through the router**, with headcanon's standard Next binding (`createNextPredictedRoot`, whose refresh is `router.refresh()`), and every Run action keeps headcanon's default finalization (`updateTag`, `refresh`, then the Ably publication). Every refresh (after an acceptance, an Ably gap, a return to the tab) goes through it. **Next's `experimental.useOffline` is on** ([NUZ-24](https://linear.app/unnamed-system/issue/NUZ-24/verify-nexts-experimentaluseoffline-with-headcanon)): a refresh or a save that fails with a network error waits for the connection and is sent again, so a lost signal does not reload the page. Verified on Next 16.3.6 with headcanon's Next binding: a refresh while offline keeps the page mounted and completes when the connection returns; a save while offline still becomes `uncertain` after the 10 s delivery wait, so the "Not saved yet" bar shows; once online, the save settles through its receipt with one commit, also after a Retry tap while offline. The flag also replays a Server Action whose response was lost after the commit (Next treats every network error as "never reached the server"); the receipt makes that replay safe. **Other failed refreshes still become a full-page load in this Next.js**: a non-OK response (a 404, a 5xx) and a build-id mismatch after a deploy. A return to the tab while the browser reports itself offline starts no refresh (`withVisibilityRefresh` holds it until the `online` event). **The queue survives the reload**: the root's `persistence` is `sessionStoragePersistence` with one key per player and Run (`run-queue:<playerId>:<runId>`), so a player who signs in to the same tab never restores another player's changes. Every change not yet accepted stays in the tab's `sessionStorage` and is delivered again under its original mutation id when the Run root mounts again, after a reload or when the player comes back to a Run they left. Receipts make the resend safe. A stored change is restored only while it matches the root's protocol: `run.v1` args only gain optional fields with no default applied when parsed, because the root silently drops a stored change whose args its schema refuses or changes; a new protocol id drops every stored change without a notice. **Accepted risk**: a reload drops open drafts (the Party editor with moves, a Drawer with typed fields, an unsaved House rules field); a closed tab drops changes not yet delivered; when `sessionStorage` is unavailable (a private window, a full store), the queue stays in memory only. headcanon's snapshot carrier (`useSnapshotRefresh`) would keep the page mounted on a failed refresh; it is not planned for version 1 and would also need [NUZ-32](https://linear.app/unnamed-system/issue/NUZ-32). The Run list is a plain server-rendered page in version 1, with no root and no axis: it reloads on navigation and on focus, which is enough for a list that changes a few times a day.
- **Recovery**: a small hook wraps `mutate` with a label per change. A refusal at prediction or acceptance (`domain`), a `replay-refused` withdrawal, a denial (`denied`), or an undeliverable change (`undeliverable`) gives a toast with the label and the reason, then a refresh to the true state; for `delivery-from-future` the reason asks the player to check the device clock. A `delivery-expired` change may still have committed before its receipt was deleted, so its toast says the change could not be confirmed and the refresh shows the true state; it never says the change was lost. A change the root delivered again after a reload reports through the root's `mutationListeners` with `restored: true`, which carry no label; when it fails, the toast says "A change made before the page reloaded was not saved." A `stale-client` result shows the out-of-date bar (below). A `delivery-cancelled` result (the Next binding handed a redirect back to the framework, which only happens when the session is gone) needs no toast: the page is already on its way to sign-in. A `root-unmounted` result is ignored. `onConflict` only logs. One status bar: "Not saved yet. Your changes are kept here." with Retry while delivery is uncertain. A freshness stall shows nothing; it is logged (with the router carrier it can only be `behind` or `missing-axis`, which mean a loader bug). A `beforeunload` prompt while delivery is not idle (a closed tab loses changes not yet delivered) or a draft is open (the Party editor with moves, a Drawer with typed fields, an unsaved House rules field); there is no in-app confirm on links that leave the Run layout (the persisted queue keeps pending changes; a Drawer is modal, so leaving means closing it first, and closing a Drawer with typed fields discards them as it does anywhere), and the Party editor and an unsaved House rules field keep their own discard confirm on Back ("Discard your changes to the house rules?"). The prompt also fires on Next's full-page load after a failed refresh; if the player stays, Next has already stopped rendering the router, so the screen no longer updates and the player must reload. The queue is kept either way. Accepted.
- **Old tabs across a deployment** (ADR 0003): **no Skew Protection.** After a deploy, an old tab's next refresh (on return to the tab, or after its own save) sees a build-id mismatch and loads the new build. A save from an old tab whose action id the new build does not know is not written by that attempt: headcanon's Next binding settles it as `stale-client`. An earlier attempt of the same change may have committed before its response was lost, so its toast says the change could not be confirmed, and the refresh shows the true state. Settlement is per change: each change behind it settles when its own delivery fails (`stale-client`, or `replay-refused` when it depends on a change that was withdrawn, such as a rename of a Pokémon whose Encounter did not save). Each failure gets its own toast, and the root shows "Your app is out of date. Refresh?" with Refresh. A settled change leaves storage; a change still pending when the player refreshes is restored on the new build and may save there. The app does not wrap the server action. From launch: migrations run before the new deployment is promoted, so the database stays usable by the previous release for the minutes of a deploy (an additive change in one step; a destructive change in two releases, with no waiting period); `run.v1` args only gain optional fields, a breaking change is a new protocol id; Refusal kinds and enum values are only added, so stored receipts stay readable; readers are lenient from launch (an unknown Refusal kind renders a generic toast, an unknown enum value renders as unknown and is never written back), so no value needs a two-step release. No version endpoint. **Action ids can survive a deploy**: Next derives them from a cached encryption key (up to 14 days) and the action's code, so an old tab may still call an unchanged action on the new build. That save commits and is followed by a refresh that loads the new build; protocol compatibility (optional args only, lenient readers) therefore holds independently of id rotation.
- **Receipts and delivery age**: the Drizzle authority keeps headcanon's defaults, a maximum delivery age (`maxDeliveryAgeMs`) of 7 days and a clock-skew tolerance of 1 hour. An older change that has no receipt is refused as `undeliverable` (`delivery-expired`). A daily Vercel Cron Route Handler calls the authority's `deleteExpiredReceipts()` and repeats while a call deletes a full batch of 1,000.

## Headcanon gaps

Headcanon is our own package, so a gap is fixed in the package rather than worked around in the app.

1. **Leaving a Run can reorder its changes.** On unmount, a predicted root sends its queued changes but skips a `sending` or `uncertain` head (`src/react/ledger.ts`, `awaitsDelivery`), and the next mount restores the head and delivers it again. When the head never reached the server, it commits after the later change: rename A fails to send, rename B is queued, the player leaves (B commits), and comes back (A commits), so the name ends as A. Receipts prevent a second execution, not a reordered one. Fix in the package before the Run screens: a root with `persistence` keeps the whole queue on unmount for ordered delivery on the next mount, instead of sending the tail after an unsettled head. [[NUZ-41](https://linear.app/unnamed-system/issue/NUZ-41).]
2. **`stale-client` drops a change that may have committed.** The ledger settles a terminal delivery error without its "may have committed" mark (`src/react/ledger.ts`, `TerminalDeliveryError`), so a change whose earlier attempt committed and lost its response settles as `stale-client` and leaves storage. The app words the toast as "could not be confirmed" either way; the package could report the mark on the failure, as it does for retries since NUZ-25. [Not blocking. [NUZ-42](https://linear.app/unnamed-system/issue/NUZ-42).]
