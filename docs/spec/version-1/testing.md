# nuzlocke.gg version 1: testing

How version 1 is tested: the seams, what makes a good test, and what is tested. It tests the behavior in [product.md](product.md) through the design in [technical-design.md](technical-design.md).

## Seams

The spec proposes two seams, as high as they go, plus a thin layer of browser checks:

1. **The Run command boundary** (the primary seam): the server actions that headcanon generates for `run.v1`, the lifecycle and membership actions (create, join, leave, start, mark, reopen, archive, try again, rename, visibility, House rules), the account actions (Display Name, delete account), and the canon loader, exercised against a real Postgres (a Neon branch or a local container) with a signed-in actor stubbed at `requireActor`. A test sends a change as a player would and reads the Run back through the loader. This one seam covers the lock, the revision, the shared `check` and `apply`, the game-data gate, the `canChange` policy, Refusals, the life-state tests of the death changes, the Chain, and the tombstone, because they all live behind it.
2. **The game data compile and reader**: the compile run on a small fixture Map (and on the three real Maps) and read back through the reader. Tests state the contract: play order, a name per Game, the Starter Place, method groups with origins, every Species of the generation, Forms with per-Game types, Evolution Line identifiers, and the permanence check against the last release.

Above both, a small set of **browser flows** (Playwright) on the real app against the same database: sign in and choose a name; make a Run and record the starter; a Soul Link join, start, death, and the partner's Shared Fate Warning with "Record death" on a second browser; a Reader on a readable and a private Run; an old tab across a deploy stays out of automation and is checked by hand.

The pure domain module (`check`, `apply`, `computeWarnings`) is the same code the server runs, so it is tested through seam 1 and, for the Warnings (Shared Fate and the derived Whiteout bar included), directly as pure functions with Run fixtures, because a browser is the only other caller.

One more small suite sits on the client: a **recovery integration suite** for the app's own glue around the Run root, with the network intercepted (headcanon's client testing helpers where they fit, otherwise Playwright with request interception). Delivery and freshness behavior is headcanon's and is tested in headcanon, not again here. The suite covers the persisted queue's configuration (one key per Run) and the restored-change notice, the change labels in toasts, the out-of-date bar, and the refresh on return to the tab (also while offline).

## What makes a good test

- It tests external behavior at the seam: a change goes in, the Run that comes out (and the Refusal or the Warning) is asserted. It does not assert row shapes, call order, or private state.
- It uses the glossary's vocabulary in its name ("a second Encounter of one Journey in one Slot is refused as slot-taken").
- It runs against a real database for anything that the database or the lock enforces. In-memory fakes of Postgres do not count for seam 1.
- Warnings are asserted as "shows while the condition holds and goes when the data changes", never as stored values.
- A Soul Link test uses two or three actors and asserts each actor's view.

## What is tested

- **Every named change** (the 15) and each account action through seam 1, including: removing an Encounter removes its Pokémon; removing a Pokémon keeps its Encounter and history; a correction edits the old line; a Party swap never exceeds six; a full Party sends a new catch to the Box; a second Pokémon for one Encounter is refused by the unique index; a Missed Encounter with no Species saves and counts for Progress and the First Encounter Rule; Correct an Encounter to another Species updates an unevolved Pokémon and leaves an evolved one, and sets or clears the Species of a Missed one; "Other species" edits the latest evolution line, removes it when the chosen Species is the one it started from, or sets the Species with no line; Record a death on a dead Pokémon, Edit a death and Undo a death on a living one are refused as `gone`; a set change whose value is already set is a no-op, not a Refusal.
- **Concurrency**: two writers to one Run serialize; two players who make a new Slot at one Place at the same time share it; one player's two devices that make the same new Slot get `slot-taken` on the second; a refusal rolls back every row and the revision; two players who tap Try again at once make one next Run; concurrent independent Rule toggles both hold; the Duplicate dependency in both directions.
- **Shared fate** (pure functions on fixtures): a partner's death marks my living Pokémon in the Party and in the Box; recording mine, the undo of every dead partner Pokémon in the Link, or turning the Rule off clears it; in a Link of three with A and B dead and C alive, undoing A keeps C's Warning and gives A one, with the cause naming B's death; a Link of three with two deaths gives one Warning whose cause names the first death; a late entry into a Link with a dead Pokémon gets the Warning; with both Rules on, a Party Pokémon with a dead partner shows only the Shared Fate Warning; with Shared Fate off, Complete Links still marks it. The Whiteout bar shows for an empty Party after a Party death and not for a Party emptied with no death.
- **Predictor and server agree**: the predictor and the server `check` give the same effect from the same state and args; a refused replay of an accepted change shows no toast and the screen matches canon; a fresh server command against a removed target is refused.
- **Each Refusal kind** through each path that applies (prediction, replay, server); `unknown-entry` is server only; an Encounter at a Custom Place passes the game-data gate.
- **Rules**: each of the nine Rules against fixtures that break it; nothing about Warnings is stored; a Reader page computes the same Warnings.
- **Actor and access**: a request for another Run's ids, a partner target outside the policy, a receipt replay by a non-member, a tombstoned actor, a Finished Run's changes, and a Waiting Run's changes (Set the Rules included) are all refused; the same envelope retried commits once; a loader read during a write never pairs an old value with a new revision.
- **Lifecycle and Chain**: the state matrix of [Run lifecycle](product.md#run-lifecycle); only the newest Attempt reopens; Archive hides the Chain and Unarchive brings it back; Try again copies name, Rules, Custom Places, House rules, visibility, players, and Games; a deleted Player removes Try again.
- **Account**: delete account on solo Runs, on a started Soul Link (tombstone, "Deleted player"), on a waiting Soul Link (leaves), and as the last living Player (the Run goes); a create, join, or Try again by a tombstoned actor is refused.
- **Game data in the Box**: National Dex order sorts by the compiled dex number through the reader seam.
- **Live**: unauthorized or mixed-axis token requests fail; a Reader gets a token for a readable Run and not for a private one, renews it, moves between two readable Runs on one connection, and sees a partner's death without changing tabs; two preview branches with the same Run id do not see each other's publications; a return to the tab refreshes the Run; a waiting Soul Link shows a join within seconds with Ably and on return to the tab without.
- **Game data**: the contract tests above on a fixture Map; for each real Map a review of the generated files' diff against the hand-written one-time encounters; the sprite build step produces a file for every Species and Form, and the first-Form fallback.
- **Reader**: a readable Run renders the Rules, House rules, and Warnings and never the fail bar, the "Record death" action, the invite link, or emails; a private Run shows the private page; a private earlier Attempt is not a link; the preview card uses public data only; `noindex` is present.
- **Recovery (client suite)**: a refresh with a non-OK response while a change is pending reloads the page, and the reloaded Run delivers the change once; leaving the Run layout with a change pending and coming back delivers it once; a restored change that the server refuses shows "A change made before the page reloaded was not saved."; two Runs in one tab keep separate queues; a player who signs out with a pending change and another player who signs in to the same tab and opens the Run do not restore it, including when the identity changes in another tab and fresh canon arrives without leaving the Run route; rename A's delivery fails before it reaches the server and becomes `uncertain` while rename B stays queued, the connection returns, and leaving the Run and coming back ends with name B (fails before the package fix); a stored change from an older build whose args still parse is restored; after an out-of-date save with several changes queued, a refresh before they settle restores the unsettled ones, and a change that depends on a withdrawn one settles as `replay-refused`; a change that committed, lost its response, had its receipt deleted, and was delivered again shows the "could not be confirmed" toast, not "not saved"; a return to the tab while offline refreshes once the connection is back; through the real Next binding, a save to an action the new build does not know settles as `stale-client` and shows "Your app is out of date. Refresh?", and an old-tab save to an action whose id survived the deploy commits once; the leave prompt for a pending change and for an open draft; typing House rules and tapping Back without Save asks to discard; a change to a partner's Journey is denied, and a change on a Finished Run is refused with a public reason.
- **Deployment** (checked by hand): an old tab across a deploy reloads onto the new build at its next refresh; a save to an action the new build does not know shows the out-of-date bar and its toast; a save that committed, lost its response, and was retried after the deploy shows "could not be confirmed"; a save to an action whose id survived the deploy commits once and shows neither. A reader renders an unknown enum value or Refusal kind without failing and never writes it back (a unit test of the lenient parse).

## Prior art

The headcanon package ships two testing entry points, and its testing guide ("choose the test boundary", "keep a small browser suite") is the pattern to follow: `headcanon/testing` (an in-memory mutation authority and invalidation adapter, for predictor tests and fixtures) and `headcanon/testing/react` (the refresh contract), which is not needed while the root uses the binding's own router refresh. The package's authority and invalidation contract suites are internal, so seam 1 and the Live tests cover our Postgres authority and the Ably adapter; the recovery suite and every domain scenario are application-written tests that render the real Run root, with the app's own Postgres harness and fixtures, which the build tickets write. The research and design tickets name the acceptance checks that the lists above are drawn from.
